# Product direction

The user wants to read source documents and keep durable annotations and Markdown notes in Obsidian, with AI assistance through an existing subscription. The assistant should know the open document and selected passage. Long documents need local processing and retrieval so individual questions do not require sending the whole document.

The first usable version targets Obsidian desktop on Linux, macOS, and Windows, with EPUB and text PDF files stored in the vault. Scanned PDFs and OCR are deferred. The plugin owns a Reader view for both formats, using bundled, pinned pdf.js and pinned foliate-js, rather than patching Obsidian's built-in PDF viewer.

The plugin manages reading context, highlights, passage notes, and navigation back to source passages. A structured JSON annotation record is authoritative; the plugin generates a Markdown annotation file for reading, searching, and linking. Each document also has a book note, an ordinary Markdown note the user owns, with a quote section for every highlight. Everything the user writes about a passage goes under its quote there, so there is one place for writing; the plugin adds sections for new highlights and removes empty ones, and never edits the user's writing. Annotation records and conversation records sync with the vault. Local retrieval extracts text with chapter and location information, then combines keyword search and local embeddings. Derived indexes live outside the vault and can be rebuilt.

The user asks questions without choosing which passages to send. The plugin supplies a selected passage and nearby text automatically. The reading assistant can then search the source document, read passages with surrounding text, read the chapter list, and read highlights and passage notes. It can request more text when the first results are insufficient. Tool results have size limits and source locations for citations. Questions about the whole source document require evidence across chapters. Chapter summaries are an improvement to test; original passages remain the evidence. The [retrieval workflow](./reading-workflow-plan.md#retrieval) records this accepted approach and the first validation checks.

The reading assistant runs through the user's installed, unmodified Claude Code or Codex CLI, chosen per conversation. Authentication belongs entirely to the CLI. The plugin must not read credential files or collect, store, or relay subscription credentials. The plugin writes its own adapters and launches the installed executables. Claude Code receives document tools through a local MCP server; Codex normally receives dynamic tools through app-server, with an MCP-based exec fallback. The [workflow plan](./reading-workflow-plan.md#assistant-cli-integration) describes each mode's capabilities and restrictions.

The assistant answers questions about a selected passage or the whole document and may use web research unless the user disables it for that conversation. It can read the document's annotations but never change them. The user can save an answer to the book note under its passage. Answers cite source passages with links that open them, link outside sources, and label the assistant's own interpretation. The plugin tracks both the current location and the furthest point read. Optional spoiler-safe mode limits every document tool to text before the furthest point read, including surrounding text and any future chapter summaries.

The implementation now includes a PDF Reader with highlights, book notes, JSON annotation records, and generated Markdown exports. EPUB, retrieval, and assistant integration remain planned. See [the PDF reader guide](pdf-reader.md) for implemented behavior and its current limits. The [reading workflow plan](./reading-workflow-plan.md) records the latest product decisions and acceptance targets, but is not yet an approved implementation plan. Reader engines, annotation authority, retrieval approach, and CLI integration direction are decided; exact versions, schemas, storage paths, and implementation sequencing still need to be worked out and validated.

The plugin is intended for public release with both CLIs. Before implementation, verify the integration against current primary documentation and vendor terms; before release, recheck those terms and Obsidian's developer policies. The current plan is to proceed without requesting vendor confirmation. If either vendor objects to this integration, its CLI adapter may have to be withdrawn.

The original requirements came from [Book Note Workflow Options](chatgpt-conversation://6ac50675-2160-83e9-8b9c-90a861c07281), read during project setup on October 6, 2026, and were refined by later product interviews. That conversation is historical context, not a guarantee about current vendor policies.
